## 一、这个 PR 做了什么

用户原始需求：「现代今日的地址不完整只有六个，我想改成可以直接定位的系统，
把中国的城市地点都加进去，像『长安』这样的地点」——随后逐步追加为：

1. **地理位置**：写死的 6 城 → **全国 361 个地级行政区**（含港澳台），自动定位
2. **真实气温**：写死的假值 `'18°'` → **Open-Meteo 真实气温**
3. **《九州地名志 · 城邑春秋》**：点城市名/漫游拉起，搜城邑看**历代沿革轴**
4. **《十二时辰养生与雅事》**：点时辰拉起，滑动体验十二时辰
5. 顺带修正两个原有 bug：**时间冻结**、**时辰后缀写死「日映」**

**版式保持原样**（左右两栏，左「现代·今日」/ 右「古代·时令」）—— 这是用户在
中途明确要求的红线，本 PR 严格遵守。

## 二、逐项说明

### 1. 地理位置（`bab50c6`）

- 新增 `utils/geoCities.js`（脚本生成）：**361 城**，含省级、经纬度、有据可考的古称
  - 坐标取数据集提供的**城市中心点**，而非全部区县算术平均 —— 实测对已知市中心
    平均偏差 **5.0km vs 28.9km**（后者会把中心拉向延庆/密云这类远郊，
    导致「天安门」被定位到廊坊）
  - 古称只收录**有确证史料**者（221 城）；深圳、石家庄等地古代无对应重要城邑，
    一律留空 —— **不臆造古称**，那等于伪造历史
  - 剔除 2 条脏数据：`县`（重庆条目解析残缺名）、
    `自治区直辖县级行政区划`（河南/湖北/海南的省级中心占位坐标）
- 新增 `utils/almanac.js`：定位降级链 **GPS → IP → 默认北京**
  - IP 服务实测选型：`ipwho.is`（HTTPS+CORS）首选、`ipinfo.io` 备用
- **未改动左右两栏版式**；`home.less` 为纯新增（126 行，0 删除）

### 2. 真实气温（`bab50c6`）

Open-Meteo（免费无 Key），按所选城邑经纬度取当前温度 + WMO 天气码
（映射为「晴明 / 云气渐生 / 细雨」等古风天气词）。取数中或失败显示「—」，
**不显示假数字**。切换城邑自动重取。

### 3. 九州地名志 · 城邑春秋（`98025a9` + `bc93f4f` + `3eef923`）

- **359 城 / 1052 条历代沿革**，格式与用户给的样例逐字一致：
  ```
  西安 → 周代〔镐京〕丰镐故地，礼乐之邦
         秦代〔咸阳〕六王毕，四海一
         汉唐〔长安〕「春风得意马蹄疾，一日看尽长安花」
         宋元〔京兆〕关中重镇，丝路通衢
         明清〔西安〕丝路起点，古都新生
  ```
- 未收录/海外城邑走典雅提示：「虽身在万里瀛海，心系九州故里」+ 江南名邑推荐
- **678 条古称别名**：输入「广陵」「会稽」「华亭」「沪」「番禺」等任一古称
  都能展开对应城邑（自动从沿革轴提取，并排除夫余/挹娄等部族名，避免误导）
- 底部「留驻此时空 · 切换时令」联动主页：左栏天气温度重取、右栏古称与诗句刷新

### 4. 十二时辰养生与雅事（`98025a9`）

- 新增 `utils/shichen.js`：十二时辰 + **雅称**（夜半/鸡鸣/平旦/日出/食时/隅中/
  日中/日昳/晡时/日入/黄昏/人定）+ 古人生活 + 养生要点 + 雅事
- 弹窗内横向滑动体验，**打开时自动滑到当前时辰**居中
- 顺带修正 bug：原代码 `{curShichen.name} · 日映` 把后缀**写死**，且「日映」
  并非十二时辰别称 → 现按真实时间显示雅称（亥时→人定）

### 5. 时间冻结 bug（`ff58d1d`）

原代码 `const dateText = getDateText()` 等三行只在首次渲染算一次，**没有任何定时器**
→ 实测系统 21:57 时页面仍显示 21:56。改为状态 + 30 秒推进，
时间/时辰/物候/节气一并随时钟走动。

### 6. 与郑小君实现的整合（`c066912`）

`team/main` 上的 `bd26be6`（同日 21:46）与本人分支是同一需求的两个并行实现。
经确认采用**整合方案**：

- **保留他的 `CITY_DICT`**（65 城逐城精编诗句与物候雅称，如绍兴「兰渚流觞」），
  作为 `cityView()` 的**最高优先级**
- 实测效果：留驻绍兴 → 「会稽（绍兴）· **20°（真实气温）** ·
  此地有崇山峻岭，茂林修竹。· 物候：**兰渚流觞**」
- 合并时修正：原有两个并行定位 effect 互相竞争，且**都只设城市未同步经纬度**
  → 真实气温会一直用初值；已合并为单一链路并统一同步坐标

## 五、遗留事项（不阻塞本 PR）

1. **同事 `ancientCities.js` 的定位链路有三处问题**（已实测，详见
   `docs/给郑小君-ancientCities定位链路问题与改法.md`）：
   - `pconline` 接口**无 CORS 头** → 浏览器 fetch 直接失败，首选链路不通
   - 备选 `ip-api.com` 是**明文 HTTP** → HTTPS 部署会被混合内容拦截
   - `pconline` 返回 **GBK** 而按 UTF-8 解 → 城市名乱码，且被缓存 12 小时

   三条都失败即恒返回默认杭州，即「自动感知」实际是写死的默认值。
   **本 PR 已在整合层加防御**（城名不可读即弃用、转走本人 `locate()`），
   先保证线上不出现乱码；根因需他本人修。修好后该防御可移除。

2. 古称仅 221/361 有史料支撑，其余留空（不臆造）
3. 沿革轴 1052 条，个别城市的分期名（洛阳「汉魏·隋唐」、沈阳「后金」）为
   跨代惯用称，非单一朝代
