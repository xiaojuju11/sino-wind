# `docs/design` — 设计稿存放与评审约定

> 本目录存放**设计稿原图与评审记录**，与代码产物隔离。规范依据：仓库根目录 `DESIGN.md`（v3）。
> 目的：让「出图 → 评审 → 落地」三步有据可查，且设计稿不污染前端构建产物。

## 一、 目录结构

```text
docs/design/
├── README.md                本约定（长期有效）
└── phase3/                  按阶段分目录
    ├── REVIEW.md            本阶段逐屏评审记录
    ├── P1-yaji.png          Stitch 导出的设计稿原图
    ├── P2-zhiyin.png
    ├── P3-zhiyin-chat.png
    ├── P4-yingqing.png
    └── P5-shuzhai.png
```

**命名规则**

| 内容 | 位置 | 命名 |
| :--- | :--- | :--- |
| 设计稿原图（Stitch 导出 / 截图） | `docs/design/<阶段>/` | `P<序号>-<拼音短名>.png`，迭代加 `-v2`、`-v3` |
| 评审记录 | `docs/design/<阶段>/REVIEW.md` | 每阶段一份 |
| 生产用切图（透明底 PNG / 背景 JPG） | `frontend/public/assets/<模块>/` | 按 `DESIGN.md` §10.1 清单命名 |
| 设计源文件（Figma / Sketch） | **不入库** | 链接记录在本文件《源文件链接》一节 |

**两条硬规矩**

1. 设计稿**不要**放进 `frontend/public/`：会被打进构建产物，也会被误当成生产素材引用。
2. 入 `frontend/public/assets/` 的只应是**最终确认的生产切图**，不是中间稿。

## 二、 评审流程（按 DESIGN.md §九 执行）

| 步骤 | 谁做 | 产出 |
| :--- | :--- | :--- |
| 1. 出图 | 设计/开发 | 按 `STITCH-PROMPTS.md` 或 `DESIGN.md` 逐屏提示词生成，存入 `docs/design/<阶段>/` |
| 2. 提评审 | 出图人 | 在 `REVIEW.md` 对应屏补上文件名与「待评审」 |
| 3. 逐条核验 | 评审人 | 按 §9.4 表格给结论：色板 / 图标位 / 圆角与阴影 / 文化准确性 / 建议改法 |
| 4. 修正 | 出图人 | 按「建议改法」重新生成，文件名升版（`-v2`） |
| 5. 归档 | 评审人 | 状态改为「已通过」，并把需要落到代码的差异补进 `DESIGN.md` §十一 |

**状态定义**

| 状态 | 含义 |
| :--- | :--- |
| `待评审` | 已出图，尚未核验 |
| `需修改` | 存在违反 §九 红线或反模式的项，附修正句 |
| `已通过` | 视觉稿符合规范，可作为切图与实现依据 |
| `已落地` | 对应代码已完成，且与稿子一致 |

**核验项与依据**

| 核验项 | 依据 |
| :--- | :--- |
| 色板 | `DESIGN.md` §2.1（8 个角色 + 1 个派生色） |
| 图标位 | §9.1 R1/R2（线性矢量图标；无位图、无 emoji、无字符箭头） |
| 圆角与阴影 | §2.3（卡片 12px / 大卡与抽屉 16px / 印章 6px；阴影 `0 4px 16px rgba(0,0,0,0.04)`，无外发光） |
| 文化准确性 | §9.2（无编造古诗与伪托出处、无简繁混排、无伪文言腔） |
| 数据真实性 | §9.1 R4（数字与文案为占位，不编造指标） |
